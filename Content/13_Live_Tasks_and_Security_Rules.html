Live Tasks and Security Rules

In the last session, the tasks finally move to Firestore. Each task becomes its own document, the app listens for changes, and the list updates by itself on every device. Then we lock the database so only you can see your tasks.

Goals

  • By the end you can listen to a Firestore collection with snapshots() and keep the screen in sync.

Concept 1

Asking once vs listening

In plain words

get() asks Firestore once and gets one answer. That's what we've done so far.

snapshots() says "tell me whenever this changes". It returns a Stream: a new answer after every change, until you stop listening.

It's like…

Calling a friend to ask the football score vs joining the group chat. The call gives you the score once. In the group chat, every new goal arrives by itself.

final db = FirebaseFirestore.instance;

// once: a Future, so we await it
final snap = await db.collection('Users').get();
debugPrint('Users now: ${snap.docs.length}');

// forever: a Stream, so we listen to it
db.collection('Users').snapshots().listen((snap) {
  debugPrint('Users changed: ${snap.docs.length}');
});
Users now: 3 Users changed: 3 Users changed: 4 (someone registered)
Everyday life

A news website you refresh vs a live sports app that updates the score on its own.

In our app

Change a task's status in the Firebase console and the app ticks it, without anyone touching the phone.

❌ Wrong: awaiting a Stream
final snap = await db.collection('Users').snapshots();
A value of type 'Stream<QuerySnapshot>' can't be assigned…

A Stream never "finishes", so you can't just await it like a Future.

✅ Right: listen to it
db.collection('Users').snapshots().listen((snap) {
  // runs on every change
});
Concept 2

One document per task, and its id

In plain words

Each user's document gets its own collection inside it: Tasks. That's a subcollection. Every task is one document there.

To change one task, we need to know which document it is. So Task gets an id.

It's like…

A filing cabinet where each student's folder has its own small drawer of homework sheets. Each sheet has a number, so you can pull out exactly one.

class Task {
  String? id;                  // NEW: the document's name
  String? title;
  String? note;
  bool? status;
  Task({this.id, this.title, this.note, this.status});

  Map<String, dynamic> toMap() => {"title": title, "note": note, "status": status};

  factory Task.fromMap(Map<String, dynamic> map, String id) => Task(
        id: id,                // the id comes from outside the data
        title: map["title"],
        note: map["note"],
        status: map["status"] ?? false,
      );
}
Everyday life

A parcel's tracking number. The shop finds your one parcel among thousands by that number.

In our app

Open Firestore → Users → your uid → Tasks in the console. Each row is one task, named by its id.

❌ Wrong: saving the id inside the data
Map<String, dynamic> toMap() => {"id": id, "title": title, ...};

The id is already the document's name. Saving it twice means it can get out of sync.

✅ Right: take it from the document
Task.fromMap(doc.data(), doc.id)

doc.id is the name; doc.data() is everything inside.

Concept 3

Growing the CRUDFirestore wrapper

In plain words

Same rule as session 11: only the service layer talks to Firebase. The controller never writes FirebaseFirestore.instance.

We add four methods next to setDocument and getDocument: listen, add, update and delete.

It's like…

A TV remote. You press "volume up", not "send infrared code 0x1F". The remote knows how to talk to the TV; you just press buttons.

Stream<QuerySnapshot<Map<String, dynamic>>> listenCollection(String path) {
  return _db.collection(path).orderBy('createdAt').snapshots(); // oldest first
}

Future<void> addDocument(String path, Map<String, dynamic> data) async {
  await _db.collection(path).add({...data, 'createdAt': FieldValue.serverTimestamp()});
}

Future<void> updateDocument(String path, String id, Map<String, dynamic> data) async {
  await _db.collection(path).doc(id).update(data); // only these fields
}

Future<void> deleteDocument(String path, String id) async {
  await _db.collection(path).doc(id).delete();
}

Everyday life

A bank teller. You say "withdraw 50". You never walk into the vault yourself.

In our app

path is just text: 'Users/kX93hPq2/Tasks'. Firestore understands nested paths written this way.

❌ Wrong: set() to change one field
_db.collection(path).doc(id).set({"status": true});

Without merge, set replaces the whole document. The title and note are gone.

✅ Right: update()
_db.collection(path).doc(id).update({"status": true});

Changes status, keeps everything else.

Concept 4

The controller listens

In plain words

startListening() listens to Users/{uid}/Tasks. On every change, it rebuilds _tasks from the documents and calls notifyListeners().

listen() gives back a StreamSubscription. We keep it, so stopListening() can cancel() it.

It's like…

A newspaper subscription. Every morning a new paper arrives. When you move house, you cancel it, or the papers keep piling up at the old door.

StreamSubscription? _subscription;   // our "ticket"

String get _path => 'Users/${FirebaseAuth.instance.currentUser!.uid}/Tasks';

void startListening() {
  _subscription?.cancel();            // never listen twice
  _subscription = _crud.listenCollection(_path).listen((snap) {
    _tasks.clear();
    for (final doc in snap.docs) {
      _tasks.add(Task.fromMap(doc.data(), doc.id));
    }
    notifyListeners();
  });
}

void stopListening() {
  _subscription?.cancel();
  _subscription = null;
  _tasks.clear();
  notifyListeners();
}
Sign in → the list fills with your tasks. Sign out → the list is empty.
Everyday life

A YouTube channel: subscribe and every new video shows up; unsubscribe and they stop.

In our app

Open the app in two Chrome tabs with the same account. Add a task in one: it appears in the other.

❌ Wrong: listening without keeping the ticket
void startListening() {
  _crud.listenCollection(_path).listen((snap) { ... });
}

No way to cancel. Sign out and in again, and two listeners run: every task shows up twice.

✅ Right: keep it, cancel it
_subscription?.cancel();
_subscription = _crud.listenCollection(_path).listen(...);
Concept 5

Write to Firestore, let the listener update the screen

In plain words

addTask, changeStatus and deleteTask only write to Firestore. They don't touch _tasks and don't call notifyListeners().

Firestore sees the change and tells our listener. The listener updates the list. One path for every change.

It's like…

Posting in a group chat. You don't also write the message on your own screen: you send it, and it comes back to you like it comes to everyone else.

void addTask(String title, String note) {
  if (/* same rules as session 8 */) {
    _crud.addDocument(_path, Task(title: title, note: note, status: false).toMap());
  }
}

void changeStatus(int index) {
  final task = _tasks[index];
  _crud.updateDocument(_path, task.id!, {"status": !task.status!});
}

void deleteTask(int index) {
  if (index >= 0 && index < _tasks.length) {
    _crud.deleteDocument(_path, _tasks[index].id!);
  }
}
Same method names and the same index, so TaskListPage and TaskTile don't change at all.
Everyday life

A shared Google Doc: you type, and you see your own text the same way your friends see it.

In our app

Delete a task in the console: it disappears from the app, even though the app never called deleteTask.

❌ Wrong: updating twice
_crud.addDocument(_path, task.toMap());
_tasks.add(task);      // and the listener adds it too
notifyListeners();

The new task flashes twice, and the local copy has no id, so ticking it crashes.

✅ Right: only write
_crud.addDocument(_path, task.toMap());
// that's all: the listener does the rest
Concept 6

Security rules: only you can see your tasks

In plain words

Test mode lets anyone read and write everything, and it stops working after 30 days. Security rules fix both.

Our rule: for anything under Users/{uid}, allow it only if someone is signed in and their uid is that uid.

It's like…

Lockers at school. The building is open to everyone, but each locker only opens with its owner's key. And the guard checking keys stands at the door, not in your app.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // a user's document and everything inside it (their Tasks)
    match /Users/{uid}/{document=**} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }
  }
}
Paste into Firestore → Rules → Publish. Then test it with the Rules Playground button.
PieceMeans
match /Users/{uid}/…"For paths like this one." {uid} grabs that part of the path.
{document=**}The user's document and everything under it.
request.authWho is asking. null means not signed in.
request.auth.uid == uid"Is it you?"
Everyday life

Your bank checks your card and PIN at the bank's side. Changing the ATM's screen won't give you someone else's money.

In our app

That's why stopListening() runs before signOut(): after sign-out, the rules would refuse the listener.

❌ Wrong: "signed in is enough"
allow read, write: if request.auth != null;

Any signed-in user can read every other user's tasks.

✅ Right: signed in and the owner
allow read, write: if request.auth != null
                   && request.auth.uid == uid;

Hands-on exercise: "Clear done tasks" for real

Add an AppBar button that deletes every finished task from Firestore. The list should update by itself.

Steps
  1. In TaskController, add clearDone().
  2. Go through _tasks. For each task with status == true, call _crud.deleteDocument.
  3. Don't touch _tasks yourself.
  4. Add an IconButton in the tasks page's AppBar that calls it.
  5. Watch the console: the documents disappear, and so do the rows.
Need a hint?

Loop over a copy, like for (final t in List.of(_tasks)), because the listener may change _tasks while you're still looping.

Recap

// task_controller.dart
void clearDone() {
  for (final t in List.of(_tasks)) {        // a copy: _tasks may change meanwhile
    if (t.status == true) {
      _crud.deleteDocument(_path, t.id!);
    }
  }
}

Quiz answers

  1. get() answers once; snapshots() answers after every change.
  2. The listener, when Firestore sends the new snapshot.
  3. It changes only status and keeps the title and note.
  4. It keeps listening: duplicate tasks or a permission-denied error.
  5. On Google's servers.
